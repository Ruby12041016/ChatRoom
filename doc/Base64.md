# Base64

Base64 是一种将任意二进制数据转换为纯文本字符串的编码方式，主要解决在只能传输文本的通道中传递非文本数据的问题。在你的聊天项目中，它用于把文件内容安全地嵌入 JSON 消息体，从而通过已有的文本协议（JSON）实现文件传输。

---

## 一、为什么需要 Base64

- **JSON 只能传文本**：你的消息协议使用 JSON 格式，不能直接放入图片、文档等二进制数据，否则会破坏 JSON 结构。
- **文本协议的历史遗留**：许多网络协议（如 SMTP 邮件、早期的 HTTP）最初只设计给可见字符，Base64 让二进制数据“伪装”成文本通过。
- **你的聊天场景**：发送方读入文件 → Base64 编码 → 塞进 JSON 的 `"file_content"` 字段 → 服务端解码后存盘，或者再编码后发给接收方。

---

## 二、Base64 的核心原理

Base64 的名字含义：**把二进制数据表示成 64 个可打印字符**，这 64 个字符包括：

- 大写字母 A-Z (26)
- 小写字母 a-z (26)
- 数字 0-9 (10)
- 加号 `+` 和斜杠 `/`（有时用 `-` 和 `_` 替代，形成 URL 安全的变体）

编码过程分三步：

1. **输入分组**：把原始字节流按每 3 个字节（24 bit）一组处理。
2. **重新划分**：将 24 bit 分成 4 组，每组 6 bit（$2^6=64$，刚好对应 64 个字符）。
3. **查表映射**：每个 6 bit 值（0~63）到上面 64 个字符的映射表转换为一个字符。
4. **填充（Padding）**：若原始字节数不是 3 的倍数，用 `=` 号补足到 4 的倍数，解码时自动去除。

### 示例：编码 "Man"

```
文本  M      a      n
ASCII 77     97     110
二进制 01001101 01100001 01101110
6bit   010011  010110  000101  101110
十进制 19     22      5       46
映射表 T      W       F       u
结果 "TWFu"
```

编码后长度变大约 **33%**（因为每 3 字节变成 4 字节）。

## 三、与项目的结合点

在聊天系统中：

- **客户端发送文件**：读入文件 → `base64_encode()` → 放入 JSON 的 `"file_content"` 字段 → 发送 `MSG_FILE_MSG`。
- **服务端处理**：接收 JSON → `base64_decode()` → 写入磁盘 `./files/xxx` → 在 `messages` 表记录文件路径。
- **接收方下载**：服务端读入文件 → `base64_encode()` → 通过 `MSG_DOWNLOAD_FILE` 返回 → 客户端 `base64_decode()` 保存为原文件。

### 为什么要两头编解码？
- 发送时编码是为了让二进制文件能放进 JSON。
- 下载时编码是因为**服务端与客户端的通信协议依然是 JSON**，同样不能直接传二进制，所以服务端必须再次编码发回。

---

## 四、Base64 的优缺点

优点：
- 兼容性好，所有文本协议都能承载。
- 实现简单，标准统一。

缺点：
- 数据膨胀约 33%，增加网络开销和内存消耗。
- 需要编解码的 CPU 开销（在现代设备上可忽略）。

---

## 五、常见变体

| 变体 | 字符集变化 | 用途 |
|------|-----------|------|
| 标准 Base64 | `+` `/` 最后可能用 `=` 填充 | 大多数场景 |
| URL 安全 Base64 | `-` `_` 代替 `+` `/` | URL 参数、JWT |
| Base64 无填充 | 去掉末尾 `=` | 某些 API 要求 |
---

Base64 本质是“桥梁”，让二进制世界与文本世界互通，在你的即时通讯系统中承载起文件传输的功能。理解其原理后，调试编解码问题就会更容易。
