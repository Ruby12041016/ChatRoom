# 方案
单一方案都有明显短板，**应该分场景差异化处理**：
- 强操作请求（注册、登录、发消息等）：轮询式同步等待
- 多步连续输入（注册填信息、改密码等）：开启推送缓存
- 空闲等待输入（停在菜单界面）：推送即时弹出 + 自动重显提示符
- 聊天会话内：当前消息实时刷新，其他会话消息静默缓存

---

## 一、单一方案
### 1. 纯“菜单前排空消息”
- 优点：改造成本最低
- 缺点：操作反馈严重滞后。比如点注册，菜单都重新刷出来了才显示“注册成功”，用户会产生“到底有没有提交成功”的困惑，线性操作感完全断裂，是最影响体验的核心问题。

### 2. 纯“全同步阻塞等待”
- 优点：操作流程线性，符合直觉
- 缺点：① 死等条件变量会直接死锁（单线程模型下，主线程卡住就没人处理消息了）；② 等待期间所有推送都收不到，失去即时通讯的意义；③ 服务器卡顿会让程序像“假死”一样，没有任何反馈。

### 3. 纯“所有推送都缓存”
- 优点：界面永远干净，不会被打断
- 缺点：完全丢失了“即时消息”的属性，别人发消息半天不知道。

---

## 二、组合方案
### 1. 强交互操作：轮询同步等待
针对注册、登录、加好友、建群这类「用户发起请求 → 明确等待结果」的操作，用**轮询+超时**的方式同步等待响应。
- **体验收益**：操作反馈是线性的，用户点了注册就等着出结果，结果出来再回到菜单。
- **技术要点**：不能用条件变量死等，用循环调用 `ProcessMessages()` 的方式轮询，既等结果，也不耽误处理推送。

补充超时处理（避免服务器卡顿导致程序假死）：
```cpp
auto start = std::chrono::steady_clock::now();
register_done_ = false;
account_.Register(uname, email, pwd, phone);

// 最多等待5秒
while (!register_done_ && running_) {
    auto now = std::chrono::steady_clock::now();
    auto duration = std::chrono::duration_cast<std::chrono::seconds>(now - start).count();
    if (duration >= 5) {
        std::cout << "\n[提示] 服务器响应超时，请稍后重试" << std::endl;
        break;
    }
    ProcessMessages();
    std::this_thread::sleep_for(std::chrono::milliseconds(20));
}
```

### 2. 多步连续输入：推送缓存
针对注册、重置密码这类需要连续输入多项信息的流程，在输入期间开启推送缓存，全部输完、提交并拿到结果后，统一弹出期间收到的消息。
- **体验收益**：用户正专注输用户名、密码、邮箱时，不会突然弹出私聊消息打断输入节奏，流程感非常顺滑。
- **适用场景**：注册流程、忘记密码流程、修改资料等多步输入操作。

### 3. 空闲菜单状态：即时推送 + 重显提示符
当用户停在主菜单、好友列表等界面，只是等待输入选择时，推送消息即时弹出，弹完自动补回“请选择：”的提示符。
- **体验收益**：保证消息的即时性，有人发消息立刻能看到；同时不会出现“提示符被冲掉，用户不知道还能不能输入”的混乱感。

### 4. 聊天界面：会话隔离
进入和某个人/某个群的聊天界面后：
- 当前会话的消息：实时刷新显示
- 其他会话的私聊/群消息：静默缓存，只提示「您有N条其他会话的新消息」，不要直接插进来打断当前聊天
- **体验收益**：聊天时专注不被打扰，同时不会错过其他消息。
