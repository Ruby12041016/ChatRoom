# 一、火焰图分析（图见附录）
## 文件传输慢的原因分析
### 1. 下载（RETR）——服务端用 `sendfile`，客户端用 `recv`
**服务端代码（`big_file.cc` 的 `do_retr`）**：
```cpp
// 线程池中运行，设为阻塞模式，避免sendfile/send返回EAGAIN
int flags = fcntl(connfd, F_GETFL, 0);
fcntl(connfd, F_SETFL, flags & ~O_NONBLOCK);
int flag = 1;
setsockopt(connfd, IPPROTO_TCP, TCP_NODELAY, &flag, sizeof(flag));
...
while (offset < st.st_size) {
    ssize_t sent = sendfile(connfd, file_fp, &offset, st.st_size - offset);
    if (sent > 0) continue;
    if (sent < 0 && errno == EINTR) continue;
    LOG(ERROR) << "sendfile失败...";
    break;
}
```
- 设置了阻塞模式（`fcntl(connfd, F_SETFL, flags & ~O_NONBLOCK)`）和 `TCP_NODELAY`，并增大发送缓冲区（4MB）。  
- `sendfile` 是零拷贝技术，理论上能将文件页缓存直接 DMA 到网卡，CPU 介入很少。  
- 火焰图（`【下载火焰图】`）显示调用栈从 `sendfile64` → `do_sendfile` → `splice_direct_to_actor` → ...，印证了内核 splice 路径。  

#### **可能原因**: 
- **网络带宽/延迟限制**：1GB 文件传输耗时主要取决于网络状况，`sendfile` 无法突破物理带宽上限。  
- **客户端接收效率低**：客户端（`cli_big_file.cc` 的 `Download`）使用 `recv` 循环读取数据并写入文件，每次最多 8MB，每次 `recv` 都涉及从内核缓冲区拷贝到用户缓冲区，再 `write` 到磁盘，存在 **两次拷贝**（内核→用户→内核），且 `write` 可能触发页缓存同步。虽然客户端也用了大缓冲区，但吞吐量受限于用户态拷贝和磁盘写入速度。  
- **磁盘读取**：如果文件不在页缓存中，`sendfile` 会触发磁盘读，IO 延迟成为瓶颈。`posix_fadvise(POSIX_FADV_SEQUENTIAL)` 只提示内核预读，但第一次读取仍需等待磁盘。  
- **热路径中的`fsync`强制阻塞**:`fsync` 是同步系统调用。在机械硬盘、虚拟机磁盘或网络存储（如 `NFS/CIFS`）上，将 256 MiB 的脏页刷回磁盘需要数百毫秒甚至数秒。在此期间，客户端的 recv 事件循环被完全阻塞，TCP 接收窗口因应用层未消费数据而降为 0。这会造成服务端`（big_file.cc）`的 sendfile 因发送缓冲区被填满（对端窗口关闭）而阻塞，导致整个下载链路出现 “发送-停止-等待” 的间歇性停滞现象。而且`SaveDownloadMeta` 内部对元数据文件的写入同样调用了 `fsync`，导致在每次断点保存周期内，磁盘同时承受数据文件和元数据文件的两次刷写压力。
---
### 2. 上传（STOR）——服务端用 `recv`，客户端用 `sendfile`  
**服务端代码（`do_stor`）**：
```cpp
while (1) {
    int len = recv(connfd, buf.data(), sizeof(buf), 0);
    if (len <= 0) break;
    fp.write(buf.data(), len);
}
```
#### **可能原因**：
- **没有使用零拷贝**，而是将 socket 数据 `recv` 到用户缓冲区，再通过 `ofstream` 写入文件。  
- 每次 `recv` 和 `write` 都产生系统调用，且数据从内核拷贝到用户缓冲区，再从用户缓冲区拷贝到内核（文件页缓存），**两处拷贝**，CPU 和内存带宽开销大。  
- 火焰图（`上传.svg`）明确显示了 `libc_recv` 和 `do_stor`，以及内核路径 `tcp_recvmsg` → `skb_datagram_iter` 等，说明大量时间花在网络接收和内存拷贝上。  
- 客户端虽然使用 `sendfile` 发送本地文件，但服务端接收的低效抵消了客户端的优势。

## 消息发送慢的原因分析
### 1. 同步数据库操作密集
在 `handle_private_chat`（`chat.cc`）中，每一条私聊消息都要经历以下步骤（均同步阻塞）：

```cpp
// 1. 检查好友关系（查 friends 表）
QueryResult check_friend = pool.Query(...);
// 2. 检查是否被对方屏蔽（再次查 friends 表）
QueryResult block_check = pool.Query(...);
// 3. 插入消息（messages 表）
uint64_t message_id = pool.ExecuteInsert(...);
// 4. 如果对方在线，推送并更新消息状态为已读（Update）
pool.ExecuteStmt("UPDATE messages SET status=1 WHERE id=?");
```

- **每次 `Query` / `ExecuteStmt` 都会从 MySQL 连接池获取连接（可能等待，因为连接数量有限）、执行 SQL、解析结果，最后归还**。网络往返 + SQL 解析 + 表锁/行锁，延迟叠加。  
- **好友关系、黑名单等**频繁查询的数据未做缓存，每次都查数据库。  
- 消息插入虽为单条，但写入 `messages` 表还涉及事务日志、索引更新，若表数据量大，插入性能下降。

### 2. 群聊消息问题更严重
`handle_group_chat` 除了检查成员资格，还要：
- 查询所有群成员（`SELECT member_id FROM group_member`），循环给每个在线成员发送推送，每个推送调用 `send_ok`（内部加锁、写 socket）。  
- 成员数多时，查询和推送成为瓶颈，且推送是同步的（虽然 `send` 内部跨线程投递，但循环中依次处理）。

### 3. 线程池阻塞与排队
WorkerPool 线程数固定（`std::thread::hardware_concurrency()`），每个消息处理任务都会长时间占用线程（等待数据库响应）。当并发消息增多时，大量任务在队列中等待，**响应延迟显著增加**。

### 4. 火焰图（`【消息发送火焰图】`）验证
火焰图顶部出现了大量 `mysql_real_connect`、`Query`、`ExecuteStmt`，以及 OpenSSL 符号（`OSSL_DECODER_CTX_new_for_pkey`），说明：
- **数据库操作占主导**，包括连接建立（可能因为连接池中连接失效导致重连，或 SSL 握手）。  
- OpenSSL 可能用于 MySQL 加密连接或密码哈希（`password_encrypt` 使用 PBKDF2，但只有登录/注册才用到了，消息模块不该出现——可能连接池每次创建连接时执行 SSL 初始化，若连接被回收复用则只执行一次，但火焰图中出现说明连接池连接可能频繁重建）。  

### 5. JSON 序列化/反序列化开销
虽然 `nlohmann/json` 有一定开销，但与数据库 IO 相比微不足道。

# 二、文件上传
## 可能原因与逐步排查：
1. 推测原因：服务端 `big_file.cc` 的 `do_stor` 使用 `recv` + `ofstream.write`，数据路径为 内核Socket缓冲区 → 用户态buf → 内核文件页缓存，存在两次CPU拷贝。同时 ofstream 默认缓冲区仅约8KB，可能导致大量小IO系统调用。

2. 操作一：
- 将 `std::ofstream` 改为 `open` + `write`，认为可绕过C++流缓冲，结果速度还变慢了。
- 分析：`ofstream` 自带的用户态缓冲区（8KB）能将多次小块 `recv` 聚合成一次 `write` 系统调用。去掉缓冲后，每次 `recv` 直接触发 `write`，系统调用次数暴增，CPU上下文切换压垮了性能。

3. 操作二：
- 保留 `ofstream`，通过 `rdbuf()->pubsetbuf(buffer, 8MB)` 将缓冲扩至8MB。结果本机和跨设备速度没有变化。
- 分析：系统调用频率已被压到最低，服务端CPU不再是瓶颈

4. 操作三：
- 将 `do_stor` 中的 `recv` + `write` 循环替换为 `splice` + 管道，消除用户态内存拷贝。本机电脑上传速度显著提高，但跨设备无任何变化。
- 分析：内存拷贝速度（20+GB/s）远快于物理链路传输速度。在低速网络下，CPU等待网卡的时间远大于拷贝时间，零拷贝优化被网络延迟完全掩盖。
---
# 三、文件下载
1. 推测原因：客户端 `cli_big_file.cc` 的 `Download` 循环中，每 256MB 执行一次 `fsync(fd)` 及 `SaveDownloadMeta`（内部再 `fsync` 元数据文件），推测会阻塞网络接收线程，造成周期性卡顿。

2. 操作一：
- 删除while 循环内的 `if (downloaded - last_checkpoint >= 256MB)` 条件块，仅在下载完全结束时执行一次 fsync，结果本机电脑和跨设备速度都没变化。
- 分析：进行`dd测试`后发现磁盘写入速度达到1.3GB/s，256MB 数据的 `fsync` 耗时仅约 0.2 秒，且该操作不频繁，用户感知不到卡顿。

```test
➜ files git:(main) ✗ dd if=/dev/zero of=./test bs=1M count=1024 conv=fsync 
输入了 1024+0 块记录 输出了 1024+0 块记录 1073741824 字节 (1.1 GB, 1.0 GiB) 已复制，0.823857 s，1.3 GB/s
```

3. 操作二：
- 将 `Download` 中的 `recv` + `write` 循环替换为 `splice` + 管道，实现 `Socket` → 文件的直接内核转发，消除用户态内存拷贝。速度无任何变化（本机很快，大约7-8秒，但是跨设备仍然保持大约10MB/s）。
- 分析：与上传同理，内存拷贝速度远高于网络传输速度。在百兆网络（10MB/s）下，CPU处理拷贝的时间微乎其微，`splice` 节省的时间完全被在网络等待时间覆盖。
